# Agent Note：每个 ingest id 只做一次尝试，以及能扛住并发的索引

Status: implemented

[English](2026-09-11-one-attempt-per-ingest.md) | 中文

> 范围：上传路由如何让客户端的一次重试不变成两份文件，以及接入索引为什么按现在的方式提交。

## 问题

上传路由只在接入记录**已经存在**之后，才会用记录回答重试。从第一个字节到记录落盘之间，两个请求是彼此独立的：它们都调用取空闲名的辅助函数，而该函数先 `existsSync` 判断、再把路径交出去——于是同时到达的两个上传可能选中同一个名字，把正文同时流进一个文件，交错出双方都没发过的字节。同名只是问题的一半：两个上传各自读出索引、加入自己的记录、再把整个文件写回，后写者的快照会把先写者的记录挤掉。而索引写入是普通的 `writeFileSync`，崩溃可能留下半截文件——读取端把无法解析的索引当作空索引，于是一次被打断的写入会丢掉里面**全部**记录。

## 决策

**路径是"抢占"来的，不是"挑选"出来的。** `reservePath` 用 `openSync(candidate, 'wx')` 创建候选文件，只有名字被占（`EEXIST`）时才顺延到下一个编号。抢占动作就是创建本身，所以同名的两个并发上传各自占有一个文件；它留下的空文件正是正文流入的目标，而 `writeBody` 的两条失败路径都会把它删掉。

**每个 id 只做一次尝试，作用域是插件实例。** `apply` 持有一张表，键是会话与 ingest id，值是仍在进行的尝试。找到自己 id 的请求会等待那次尝试，并按它的结果作答——已存下，或被拒绝——尝试结束时就把它从表中移除，因此之后的重试是**全新的尝试**，而不是重放一次失败。在尝试结束后才到达的重试仍然读记录，也就是这次改动之前就有的那条路径。这张表是**注册期状态**而非模块级状态：它的寿命恰好等于那些能用它作答的路由。

**索引提交是"加锁的读-改-写 + 原子替换"。** `recordIngest` 在索引文件的 `withFileLock` 之下运行，并通过 `writeFileAtomic` 写入，因此并发的接收会串行化而不是互相丢记录，也没有读者会看到半截索引。`readIndex` 保持无锁：rename 才使得"要么完整的旧文件、要么完整的新文件"成为可观察的事实。

**摘要是随着正文流过就算出来的**，因此记录"收到了什么"永远不需要把几 MB 的文件再读一遍。

**记录里带上媒体类型**，由 `contentTypeForPath` 从写入后的文件名推导，读索引的人不必再自行推导。该字段在读取时是可选的：早于它存在的记录依然有效，而需要该类型的读者从路径推导，而不是编造一个。

**先写文件，后写记录。** 两者之间崩溃会留下一个无人指名的孤儿文件，任何人看一眼目录就能发现；反过来则会留下一条指向不存在文件的记录，而重试会把它当作"已完成上传"回放。代价是一份重复副本，选择它，而不是选择对"收到了什么"说一句假话。

## 考虑过的替代方案

- **把整个上传都串行化在索引锁上。** 否决：那把锁的期限是两秒，让手机流式上传 64 MiB 时一直持锁，会让排在后面的每个上传都失败，而真正需要保护的只是那条记录。
- **回答重试时把文件读回来核对。** 否决：重试要为此付出一整个正文的 I/O，去重新确认记录里已经写明的事实，而摘要在流式写入时是顺手得到的。
- **把正文留在内存里，只写一次。** 否决：单请求上限是 64 MiB，而这条路由存在的意义就是让大正文不占堆。
- **对并发重复请求回一个冲突状态。** 否决：那次重试是客户端在连接中断后做出的正确动作，回冲突等于把重试循环推给每一个客户端，而这件事 host 一次就能定下来。
- **无论有没有 ingest id 都记录。** 否决：不带 id 的上传是有意的一次性行为，记录它会让索引变成第二份目录清单，还可能与目录本身不一致。
- **先提交记录再写文件。** 否决：那样索引就可能指向从未写入的字节，回放它会告诉客户端"上传已存下"，而实际上什么都没存。

## 影响

客户端的重试在上传的**整个时间窗内**都是幂等的，而不只是完成之后；两台手机同时上传同名照片会得到两个完整的文件，而不是一个被交错写入的文件。索引可以当作"收到了什么"的记录来信：条目在锁下加入、文件原子替换，因此并发接收不会挤掉对方的条目，崩溃也不会把它截断。一次上传仍然是"写一次文件 + 加锁重写一次小小的索引"，而锁只在写那段 JSON 时持有。

## 验证

`packages/workbench/workbench-bytes/tests/route.spec.ts` 通过真实 `WebServer` 驱动已注册的路由：在自己的选择仍在写入时到达的重试，会由那次尝试以 `repeat: true` 作答；同名两个上传同时到达会得到两个文件，每个文件的内容恰好是**一份**正文，且索引里两条记录都在；被拒绝的尝试既不留记录也不留文件；不是重名冲突的写入失败会作为服务端失败上报，而不是被顺延编号；记录里带有写入文件名对应的媒体类型。记录校验矩阵覆盖了闭集之外的设备、正确桶内的嵌套路径，以及空的媒体类型。
