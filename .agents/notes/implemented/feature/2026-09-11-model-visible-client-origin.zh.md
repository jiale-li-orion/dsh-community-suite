# Agent Note：提示来自哪个客户端，是模型可见的事实

Status: implemented

[English](2026-09-11-model-visible-client-origin.md) | 中文

## 问题

提示链路上**没有任何东西说明消息来自哪条连接**。客户端调用 `api.sessions.prompt`，Host RPC 走到 `agent.send`，`session.append('user/message')` 写下消息——带着文本与附件，却不带产生它的客户端。于是当模型被要求在手机上做事时，它无法知道人正握着一部手机：它会写桌面端的指令、给出对方到不了的路径、按桌面的篇幅作答。

同一个会话被两台设备同时驱动之后，这个缺口更明显：手机上敲的提示与电脑上敲的提示写下的是**不可区分**的事件，模型与日志复核者都无法判断某条指令是冲着哪块屏幕说的。

## 决策

**设备类别随 prompt 负载走，而不是随传输层走。** 客户端**每页取样一次**自己的类别，并在每次 `sessions.prompt` 时带上——正如它已经在带浏览器时区。`clientTimeZone` 是**先例也是模板**：客户端声明的事实，由 Host 校验并绑定到那一条持久化用户消息，之后由请求上下文插件读取。**传输层被否决**。

**只有三个粗粒度档位：`mobile-app`、`mobile-browser`、`desktop-browser`。** 这就是读者能据以行动的信息——为小屏作答，或为工作站作答。**不采集设备名、型号或地址**，因为一个相信了错误细节的模型，比一个什么都不知道的模型更糟。只有手机薄壳能知道自己是 App，所以由它在加载的 URL 上自报；浏览器只上报平台暴露的粗粒度屏幕类别；**没有页面可分类的运行时什么都不报**，Host 记录为空而不是编造默认值。

**Host 按闭集拒绝越界值**（`invalid-client-device`，在起 turn 之前），因此生产者 bug 无法把第四个档位写进会话日志、留给消费端去猜。

**每轮只对模型陈述一次**，在开启该轮的那一步，取材于该轮持久化的消息。`@deepseek-ai/dsh-client-origin` 在 `agent/pre-step` 读取它们并注入一条 plugin 来源的消息。同一轮内互相矛盾时如实写成 `mixed` 并列出全部档位，而不是塌缩成最后一个写入者；**没有任何声明的轮次不注入任何内容**，这使所有客户端不上报类别的部署与改动前逐字节一致。

## 考虑过的替代方案

- **从传输层推导类别**——RPC 层必须把一次调用映射回一条连接，而每一处这样的映射都是答案可能出错的新位置；它也无法从会话日志重放。
- **更细的设备身份（设备名、型号、地址）**——一个相信了错误细节的模型，比一个什么都不知道的模型更糟。
- **客户端不上报时填入配置的默认类别**——Host 记录为空而不是编造默认值，这些部署的请求因此与改动前逐字节一致。
- **按会话陈述一次、而不是按轮陈述**——同一个会话可能被两台设备同时驱动，按会话陈述对另一台设备的轮次就是错的。

## 影响

模型被告诉的内容**正是日志能重放的内容**：类别持久化在用户消息上，未来的读者或重建的请求看到的是同一个事实——不必新增第二条记录就满足"模型可见 ⟺ 已记录"。

注入是加法式的，且由**事实**而非配置决定开关：没有客户端类别就没有注入，因此既有快照、headless 运行与 ACP 流量都不变。

来源的 `kind` 仍是 `'user'`：模型面不带传输词汇，措辞由消费端决定；第二个消费端想要不同措辞时，读同一个字段即可。
