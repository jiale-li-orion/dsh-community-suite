# DSH 阶段性开发计划 Spec v0.1

日期：2026-09-09。状态：规划草案。基线：本地提交 `8353ea6`、[DSH 进化日志](../DSH进化日志.md)及本目录材料。本文规定阶段范围、依赖、交付物与验收条件；不表示这些新增能力已经实现，也不启动部署或功能开发。

**目标：让现有 PC/WSL DSH 成为手机随时可访问的个人 Agent 工作台，再以可授权、可追溯的工具调用接入手机本地能力。**

架构：近期由 PC 持有会话、上下文和任务执行的唯一权威，手机复用同一 Web 应用。手机独有能力通过插件与设备协议接入；按每次工具调用选择执行节点，不复制一套手机 Agent Loop。

技术基线：Cordis 插件、TypeScript、现有 Web 客户端与 Typert RPC、session event log、attachment/fs/approval 能力、Tailscale 私有网络。原生 Android 技术选型在 Web 能力缺口得到实机证据后确定。

## 2. 范围与设计约束

首个可交付版本是 **E0–E2：安全可达、手机好用、内容能交给 PC 的 Web 工作台**。E3–E4 构成第二个独立交付版本：PC Agent 可以经过授权调用手机能力。E5 只规定后续进入条件。

| 规则 | 必须满足的行为 |
| --- | --- |
| 单一会话事实 | 每个 session 的消息、审批结果和工具结果由 PC 日志承载；手机无权维护另一份可写会话历史。工作区仍按会话选择，不把整个产品限制成一个目录 |
| 模型可见信息可重建 | 上传内容、设备选择、影响请求的能力清单和观察结果通过已有或新增 session event 记录；心跳不逐条灌入上下文 |
| 插件扩展 | 设备服务、传输提供方、工具消费者通过现有扩展点接入；不在 agent-loop 中增加手机分支 |
| 网络与授权分开 | `trustedHosts` 是请求 authority 的信任配置，不是用户登录或设备配对。Tailnet 可达、DSH 授权和手机 OS 权限分别验证 |
| 共享业务、本地展示 | 会话与任务共享；视口、滚动、输入草稿、文件预览和壁纸默认本地。现有工作台开关仍共享，收窄视口只改变呈现 |
| 人发内容与 Agent 调设备分开 | 人在手机选择图片上传可在 E2 完成；PC 主动要求手机拍照需要 E3 的设备身份、权限和调用语义 |
| 明确处理失效 | 断网不取消 PC 本地任务；PC 不可用时明确显示连接中断。结果不确定的外部动作不得自动重做 |
| 部署参数可配置 | 上传限额、有效期、心跳、超时、允许的能力及并发限制由所属插件 Config 校验；协议版本和身份验证要求不由模型修改 |

本轮不包含离线手机 Agent、双写会话复制、CRDT、自动主节点接管、公网多租户、root/无障碍全机操控、持续录音、无人值守物理执行，以及通用动态代码安装能力。

## 3. 路线选择与阶段依赖

采用“现有 Web → 移动内容入口 → 最小设备协议 → 薄原生能力”的顺序。直接开发完整 Android App 会提前增加客户端和运行时维护成本；先做通用分布式调度器缺少真实能力负载。两者均不作为近期主线。

```text
E0 访问与运行基线
  → E1 移动 Web / PWA
  → E2 内容接入闭环             [交付 A：移动个人工作台]
  → E3 最小设备协议与工具接入
  → E4 薄 Android 能力          [交付 B：手机能力扩展]
  → E5 多节点与物理能力评估     [条件满足才启动]
```

以下编号使用 E0–E5，避免与日志里的工作台 Phase 编号混淆。v0.2 的 Native Bridge 与 Capability Protocol 阶段在此调整顺序：先规定可验证的协议，再接真实手机能力。

工期仅为单名熟悉仓库的开发者的初始工作量估算，不是日历承诺：E0 为 1–2 人日，E1 为 3–5 人日，E2 为 4–6 人日，E3 为 5–8 人日，E4 为 5–8 人日。证书配置、实机权限、外部服务和评审等待另计；E0 完成后按实测重新估算，E5 不提前排期。

## 6. E2：手机内容进入 PC 任务

**交付物：** 图片、PDF、URL 和文本从手机进入明确的 session/workspace，经用户确认后触发任务，并在 PC 工作台查看产物。

- [ ] 建立一个内容接入服务，供文件选择、粘贴与分享入口共同调用；共享目标选择、大小限制、来源记录和失败处理。
- [ ] 图片复用现有 image attachment；PDF 等普通文件写入所选会话工作区内的受控接收目录，并在消息中提供引用，不伪装成 image attachment。
- [ ] 接入请求具有稳定的 `ingest_id`，记录内容摘要、MIME、字节数、接收时间、目标 session/workspace 和来源类别。普通浏览器无法证明稳定设备身份时，只记录实际可知来源，不生成虚假 node 身份。
- [ ] 上传完成与提交用户消息分开。先展示目标和附件预览，再由用户发送；重复提交同一 `ingest_id` 返回同一结果，不重复创建用户消息或任务。
- [ ] 支持浏览器能力检测后的 Web Share Target；不支持时提供页面内上传、粘贴的同等入口。分享 POST 不绕过既有请求信任与防跨站伪造要求。
- [ ] 限额、MIME 验证、名称规范化、工作区围栏、部分上传清理和过期策略由服务端负责；模型不能指定任意上传落盘路径。上传源 URL 不自动变成网络抓取请求。

**验收：** 从手机相册、PDF 分享、浏览器 URL 分享及文本粘贴各完成一次“选择目标 → 上传/预览 → 发送 → PC 处理 → 双端查看结果”。超限、无效类型、越界路径、目标会话删除、上传中断及重复提交均有明确结果；失败不生成半条用户消息，恢复不重复启动任务。模型从会话日志可重建已发送内容。

**涉及位置：** 复用 [attachment](../packages/attachment/attachment/README.md)、[attachment-local](../packages/attachment/attachment-local/README.md)、[API proxy](../packages/host/apiproxy/README.md)、[客户端会话服务](../packages/client/runtime/src/client/sessions/service.ts)与 fs 服务。建议新增 `packages/mobile/mobile-ingest/`、`packages/client/ui-mobile-ingest/` 以及真实组装场景 `apps/web/tests/mobile-ingest.e2e.ts`；这是拟建位置，不是现有 API 承诺。服务端接收完成、引用创建和消息提交的恢复规则须在该阶段实现计划中具体化。

**交付 A 验收脚本：** 用户在移动网络下从手机分享一张图片和一份 PDF，选择已有会话并发出处理要求；关闭手机页面，PC 完成任务；用户重新进入同一会话，在文件面板看到产物。视觉路径使用实际支持图片的模型；PDF 处理能力按现有工具实测，不宣称模型原生接受 PDF。

## 7. E3：最小设备协议与 DSH 工具接入

**交付物：** 一套经过故障注入验证的设备协议、PC 插件及可运行的测试设备端。第一项能力使用无外部副作用的 `device.info`，不在协议尚未验证时实现五套 Android adapter。

### 7.1 首版语义

| 对象 | 必须定义的字段与行为 |
| --- | --- |
| 配对 | 人确认设备名称与配对请求；凭据绑定稳定 `node_id`，支持撤销。IP 地址不能充当身份；明文凭据不进入会话日志 |
| Manifest | `protocol_version`、`manifest_version`、`node_id`、能力 ID、参数 schema、权限要求、可用状态、前台要求、并发类别、副作用类别、隐私类别；不兼容版本明确拒绝 |
| Invocation | `call_id`、`session_id`、`target_node`、`capability_id`、`args`、deadline、`idempotency_key`、审批引用；同一 key 不允许携带不同参数 |
| Result | 关联原调用、终态、数据或错误、观察时间、来源节点与耗时；大对象引用 canonical artifact，不反复内联传输 |
| 生命周期 | 在线状态由连接和 lease 决定；断线/过期后禁止新调用，重连重新认证并提交 manifest；插件卸载释放注册、连接、计时器和资源占用 |
| 授权 | 已配对设备、会话授权范围、DSH 审批、本地 grant 和 OS permission 全部满足才执行；设备端复核，不信任模型提交的审批策略 |

首版设备主动连接 PC 的认证通道，在该通道上双向交换调用与结果，减少手机监听端口的部署要求。与已有浏览器 RPC 的注册和鉴权分开；实现时复用现有传输库，传输模块不承担工具权限决策。

模型使用受控的设备能力工具入口，首版只开放实现过的能力及参数 schema，不直接把任意设备上报的描述拼成可执行工具。多设备时显式提供 `target_node`；目标不在线、权限不足或能力不存在时失败，不静默换一台设备执行。

### 7.2 调用状态与结果不确定性

```text
pending → approved → dispatched → running → succeeded / failed
        → denied
pending / approved → cancelled / expired
dispatched / running → cancel_requested → cancelled / succeeded / failed / unknown
dispatched / running → unknown
```

`unknown` 表示调用可能已经产生效果而最终结果尚未证实，不等于失败。设备在执行副作用前持久记录幂等键与参数摘要；PC 重启后先对账在途调用。已确认完成的重复调用返回原结果，结果丢失但状态不明的调用需要查询或人确认，不能靠重新发送来恢复。

取消是请求，不能撤销已经发生的拍照、打开 App 等动作；界面只能在设备确认停止后显示 cancelled。审批超时、dispatch 前过期的调用禁止执行；时钟与 deadline 校验在协议中定义容差，不依赖两端时间完全一致。

### 7.3 实现范围与验收

- [ ] 以 Definition / Provider / Consumer 三个职责组织 `packages/device/device/`、`packages/device/device-remote/`、`packages/device/tool-device/`；第一版把 registry、lease 与传输实现聚合在 provider 内，避免为每个名词创建一个包。
- [ ] 利用 [工具扩展点](../docs/tool-execution-pipeline.md)与[交互能力](../packages/interaction/README.md)接线；定义 branded ID、JSON/wire 校验和配置失败条件。
- [ ] 调用、审批、有效能力快照、目标选择和模型可见结果关联 session event；设备心跳与高频诊断留在运行态或遥测，避免持续改变模型请求。
- [ ] 实现受控测试节点，并在真实可运行示例 `examples/mobile-device/` 中验证模型调用与回放，而非只有 mock 单元测试。
- [ ] 验证未知设备、凭据撤销、错误版本、非法参数、陈旧 manifest、重复 key 参数冲突、lease 过期、取消竞态、回包丢失与 PC/设备重启。

**验收：** 已配对节点的 `device.info` 完成一次真实工具往返；未配对节点零执行。模拟副作用计数器在重复投递和重启后最多执行一次；无法证明完成的情形显示 unknown。日志回放保留目标、授权结论和结果；插件卸载后无存活连接和计时器。新增 SessionEventMap 语义时同步 TypeScript/Python SDK 预期输出。

## 8. E4：按缺口引入薄 Android 能力

**进入条件：** E2 实机记录证明某项需求无法由目标手机上的 Web API 完成，且 E3 协议通过验收。仅为已有 WebUI 再包一层 WebView，不构成进入理由。

**2026-09-11 修订（用户确认）**：新增一条**独立于设备能力**的进入理由——「薄壳 App」用于接管**浏览器这一层**。实机记录（见进化日志 00:20–01:10）显示，目标手机用的是 vivo 自带浏览器：它不遵守 `cache-control`、不支持 PWA 安装（「添加到桌面」只是网页快捷方式）、后台回收长连接、并使用自己的 DNS 解析层。这些不是 Web API 的能力缺口，而是**宿主浏览器不可控**造成的；同一台机器上用 Chromium 实测，服务端的缓存策略本身正确（第二次加载 44 个 bundle 全部命中缓存、网络传输 0 字节）。因此薄壳 App 的范围严格限定为四件事：**资源本地化、launcher 图标、前台服务保活、回环代理**（域名本地映射以绕开系统 DNS，同时回环地址在规范里算安全上下文，可恢复剪贴板与 `crypto.randomUUID()`）。它不承载 LLM 密钥、不复制会话存储、不改 Agent Loop，也不替代 E3/E4 的设备能力协议——设备能力仍按原条件另行进入。

**交付物：** 独立于浏览器 Activity 生命周期的最小 Android capability service、设备状态与撤销界面，以及一条真实手机调用闭环。PC 的 Web 应用仍是主要界面，APK 不承载 LLM 密钥、Agent Loop 或第二份会话存储。

| 批次 | 能力 | 授权与验收 |
| --- | --- | --- |
| E4a | `device.info`、`camera.capture` | 配对后读取设备基本状态；每次拍照由用户在场确认，通过系统能力采集并返回 PC artifact 引用 |
| E4b | `file.pick`、`location.get` | 文件由用户选择，位置明确精度与采样时间；权限拒绝、撤销和旧位置不可冒充当前观测 |
| E4c | `microphone.sample`、`intent.open` | 一次性、有限时录音；Intent 使用允许目标集合与逐次确认，未知外部副作用不自动重试 |

- [ ] 先交付 E4a；只有真实使用提出需要时再排 E4b/E4c，不将全部能力作为首版阻塞项。
- [ ] Web/PWA 能完成的主动采集继续留在 Web；Native 只补远程调用、本地权限和 OS API 缺口。
- [ ] 锁屏、切后台和 OS 撤权时主动报告可用性变化；进程被回收或网络失联而无法报告时，由 PC 的断线检测与 lease 到期收回可用状态。不假定后台可以自动拉起相机或权限对话框。
- [ ] 相机和麦克风按设备资源串行；设备端确认后才上传。标记 local-only 的数据不得上传，derived-only 只有存在已验证的本地转换能力才可使用，否则拒绝。
- [ ] 记录协议兼容区间；WebUI 普通更新不要求 APK 更新，协议不兼容时明确提示版本问题。

**交付 B 验收脚本：** 用户从 PC 会话要求使用指定手机拍摄；手机显示请求与授权目标，用户确认后采集；图片进入 PC 会话，模型处理并输出产物。重复投递不再次拍摄，上传开始前收到取消或撤权则禁止上传；上传已开始时停止后续传输并报告实际状态，不宣称撤回已经传出的字节。手机离线时返回明确错误，PC 本地工具仍可独立运行。

建议原生项目放入 `apps/android-capability/`，PC 适配继续使用 E3 的包，设备面板通过 `workbench.panel` 注册。原生语言、最低 Android 版本与后台执行方式在 E4a 的实现 spec 中由目标手机实测确定，不照搬社区仓库的历史能力表。

## 9. E5：多节点与物理能力的进入条件

| 方向 | 启动证据 | 第一次实验的范围 |
| --- | --- | --- |
| 第二计算节点 | 至少一个真实任务因 PC 算力、数据位置或设备局部权限需要其他节点 | 加入一台 server/tablet，显式选择目标，记录时延、传输字节和失败；不先做自动最优调度 |
| 网络/隐私感知调度 | E3/E4 已收集到可比较的节点性能与隐私约束 | 比较原始数据迁移、派生观测迁移和延迟执行；每次选择可解释且可回放 |
| 语音与环境观察 | 用户确需持续交互，且一次性采集不足 | 从按键语音或单个 sensor 开始，定义采样时效、授权期限、停止操作和功耗测量 |
| BLE/物理执行 | 有具体设备、可测副作用和人工停止路径 | 限定单设备与单动作，先处理授权、资源占用、重复调用和紧急停止 |
| 会话复制/备用协调节点 | PC 不可用已反复导致无法接受的任务中断 | 单独编写状态所有权、冲突与接管 spec；证明一个任务不会被两个协调者同时提交 |

v0.2 中 Malleable Systems、LIVE、Ink & Switch 等材料保留为研究参考。对象检查器、可操作执行轨迹和 artifact 版本关系可各做小实验，但不与移动工作台首版绑定验收；不从研究方向直接推导当前包结构。

### 10.2 测量标准

每个交付版本至少记录 10 次正常操作和 5 次断线恢复，列出客户端/服务端版本、网络路径、成功数、失败原因、p50/p95；小样本统计只作回归线索，不作稳定 SLA。模型耗时、网络耗时、用户审批等待与 OS 执行时间分开记录，跨设备时间戳比较须注明时钟误差。

## 11. 首轮开发顺序

1. 执行 E0，确认 HTTPS、信任配置和运行生命周期；产出移动访问部署与验收记录。
2. 执行 E1 的窄屏工作台与审批路径，复用现有 PWA manifest，完成真机使用验证。
3. 执行 E2 的页面内图片/PDF/URL/文本接入，再增加受支持的分享入口，验收交付 A。
4. 根据交付 A 的真实限制决定是否启动 E3；先做 `device.info`、调用状态与失败恢复。
5. 仅在 Web 缺口明确时执行 E4a 拍照闭环，验收交付 B；其余手机能力和 E5 单独排期。
