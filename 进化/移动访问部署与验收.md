## 2. 运行拓扑与监听位置

```text
手机 (Android, tailnet)
  └─ https://node.tail0d75db.ts.net/  ──┐
                                        │ tailscaled (Windows, PID 7132)
Windows 主机                            │  100.77.160.68:443  HTTPS Serve
  ├─ 100.77.160.68:443   HTTPS ────────┘  100.77.160.68:3082 HTTP Serve（旧链路）
  ├─ 0.0.0.0:3081        TCP 转发（旧链路，开机自启）
  │     └─ win-tcp-forward.py 0.0.0.0:3081 → 127.0.0.1:3080
  └─ 127.0.0.1:3080  ← mirrored 网络回环中继
        └─ WSL: dsh web 监听 127.0.0.1:3080（仅回环）
```

`dsh web` 只绑 `127.0.0.1`，`--host 0.0.0.0` 被[启动参数](../packages/bundle/web-app/src/startup.ts)明确拒绝；手机可达性完全由上面的 Windows 侧监听承担。Windows 与 WSL 之间靠 `networkingMode=mirrored` 的回环中继互通：Windows 里的 `127.0.0.1:3080` 实际就是 WSL 的监听器（Windows Edge 打开 `http://127.0.0.1:3080` 实测 200）。

## 4. HTTPS 入口

`tailscale serve status`：

```text
https://node.tail0d75db.ts.net (tailnet only)
|-- / proxy http://127.0.0.1:3080
http://node.tail0d75db.ts.net:3082 (tailnet only)
|-- / proxy http://127.0.0.1:3080
```

TLS 实测（Windows 侧 python 探测，见 `e0_tls_probe.py`）：`TLSv1.3` / `TLS_AES_128_GCM_SHA256` / ALPN `h2` / 证书 `CN=node.tail0d75db.ts.net`、SAN 同名、签发者 Let's Encrypt `YE2`、有效期 2026-09-10 → 2026-12-09。证书由 tailscaled 自动续期，公开受信，Android Chrome 无需额外信任配置。

真实 Chromium（Windows Edge 152，`--no-proxy-server`）打开该 origin 返回完整启动页（含 `window.__DSH_BOOT__`）。手机使用的是同一条链路，差别只在设备位置。

## 5. authority 与特权策略

`~/.dsh/profiles/web/cordis.patch.yml`：

- `web-runtime.trustedHosts` 与 `connection.trustedHosts` 都追加 `node.tail0d75db.ts.net` 与 `100.77.160.68`；loopback 默认受信，无需列出。
- `connection.privilegedAuthority: trusted` —— **当前启用**。没有它，手机上的设置面板、凭据、preset 名单和"添加工作区"全部 403。

这是有意的部署决策，也是与计划措辞（"仅在需要手机管理设置时启用"）的差异点：手机既要看会话也要改设置，所以启用。风险面是"任何通过信任栅栏的 tailnet 客户端都能调用特权方法"，缓解手段是 Serve 限 `tailnet only` + 设备需在 tailnet 内。若要收回，把该行的 `privilegedAuthority` 去掉并重启即可，其余功能不受影响。

`e0_smoke.py --privileged-status` 就是为这个策略位准备的：它把期望值钉死，策略被无意翻转时探测失败。

**首次加载被误判为卡死**：手机在 `Loading plugins…` 停留较久，用户一度认为打不开。实测首次加载载荷 **11.70 MiB / 48 个请求**，其中 **7.0 MiB（60%）是单个第三方 bundle** `@dsh-external/dsh-client-ui-skin-maid-atelier`（女仆皮，内联资源）。服务端**不压缩**：客户端带 `Accept-Encoding: gzip, br` 时响应仍无 `Content-Encoding`。经 DERP 中继的移动网络下这就是"像卡住"的原因。E1 的两个候选优化：host 侧启用压缩，或把该皮肤拆出首屏。

2. **断开后重连、PC 任务继续**：手机断网期间 PC 任务不受影响，手机恢复后能读回最终结果。

## 8. 已确认的陷阱（影响后续所有探测）

1. **WSL 够不到 tailnet HTTPS，不要据此判定服务故障**。mirrored 网络把 Windows 的 Tailscale 地址 `100.77.160.68/32` 也分给了 WSL 的 `eth0`，WSL 内该地址被当成**本机地址**（`ip route get` → `dev lo`），所以 `100.77.160.68:443/3082` 在 WSL 内一律 `Connection refused`。**Windows 侧和手机走的是同一条可用链路。**任何 HTTPS 入口探测都必须在 Windows 侧执行。
2. **系统代理（Clash，`127.0.0.1:7897`）会污染探测**。WSL 里 `HTTP(S)_PROXY` 已设置，而 `no_proxy` 不含 `100.*`。表现是把 tailnet 请求交给代理后拿到 **502 + `Proxy-Connection` 头**，看起来像"服务挂了"。要么 `--noproxy '*'`（curl）、要么在 WSL 里显式绕开代理。
3. **`agent-browser` 默认驱动的是 WSL 自带 Chromium，不是 Windows Edge**。`connect 9222`／`--cdp 9222` 实测都没有真正接管 Windows Edge（`get cdp-url` 返回的是自己新起的实例，UA 为 `X11; Linux x86_64`），于是又撞回第 2 条的代理 502。要拿"真实 Windows 浏览器"的证据，用 `msedge.exe --headless=new --no-proxy-server --dump-dom <url>` 一次性输出，比接 CDP 可靠。
4. 命名 session（`--session <name>`）需要可写的 `XDG_RUNTIME_DIR`；当前沙箱下 `/run/user/1000` 只读，需指向工作区内的目录。

## 8.1 手机侧故障诊断（2026-09-11 实测）

手机报 `ERR_NAME_NOT_RESOLVED`（Chrome -105）、换 `https://100.77.160.68/` 报 `ERR_SSL_PROTOCOL_ERROR`（-107）。这两条错误码组合起来已经能定位，不必逐个试：

- **-107 不是网络不通**。只有在 TCP 已经连上、开始 TLS 握手之后才会报 SSL 协议错误；用 IP 访问失败是因为 **tailscaled 只按配置的主机名（SNI）发证书**，SNI 对不上就直接断握手。
- **按 IP 走旧 HTTP 入口也不行**：`http://100.77.160.68:3082/` 返回 `404 page not found` + `X-Content-Type-Options: nosniff`——这是 Go 的 `http.NotFound`，即 **tailscaled 自己答的**，说明 serve 只匹配 `node` 与 `node.tail0d75db.ts.net` 两个主机名。**绕开 DNS 的入口不存在**。
- **三个探测层的结论**：`tailscale ping`（disco，145ms via DERP tok）通；`tailscale ping --tsmp`（WireGuard 数据面，169ms）通——它的说明是 "through WireGuard, but not either host OS stack"；但服务端 `netstat` 一条来自手机的连接都没有。**隧道好、手机 OS 没把包送进去**，于是连 Tailscale 的 DNS 也没被采用，最终表现就是解析不了域名。
- **手机侧重置顺序**：① 确认没有第二个 VPN/代理 App 占用 Android 唯一的 VPN 槽位（梯子类 App 会把 Tailscale 顶掉，而 Tailscale 界面仍可能显示"已连接"）；② Tailscale App 内确认 **Use Tailscale DNS** 开启；③ Android 私人 DNS 改成"自动"；④ 在 Tailscale App 内断开→重连（用飞行模式切换不会重新接管 DNS）；⑤ 把 Tailscale 的电池策略设为"无限制"（国产 ROM 会杀 VPN 服务）。
- **本次结论**：服务端与 tailnet 全程正常（49 个资源在真实 HTTPS + 压缩下全部 200、总下载 6.22 MiB），故障在手机侧的名字解析。

## 9. 启动、停止与恢复

| 动作 | 命令 / 位置 |
| --- | --- |
| 启动 dsh web | 桌面快捷方式 `dsh-web.sh`（WSL 前台，关窗即停） |
| 停止 dsh web | 关闭该控制台窗口或 Ctrl+C |
| 转发（旧链路） | 开机自启 `Startup\DSH Web forward.lnk` → `pythonw win-tcp-forward.py 0.0.0.0 3081 3080`；停用 `forward-stop.cmd` |
| Serve 配置 | Windows：`tailscale serve status`；重建 `tailscale serve --bg --https=443 http://127.0.0.1:3080`；清空 `tailscale serve reset` |
| 改 profile 后 | 必须先 `--dump-config` 自检再重启进程，否则客户端会因 profile/进程漂移报 `Failed to load plugins` |
| 恢复 default 策略 | 删除 `connection` patch 行的 `privilegedAuthority: trusted`，重启 |

## 10. 旧链路收敛

`0.0.0.0:3081` 转发与 `http://…:3082` Serve 保留为 HTTPS 的退路，**等手机在 HTTPS 上完成第 7 节第 1 项验收后再按实际部署范围收敛**（计划第 4 节退出条件）。届时优先停掉 `0.0.0.0:3081`——它绑在所有接口上，虽然 `WLAN` 方向被 Windows 防火墙（Public）挡住，但收敛后不再需要它。
